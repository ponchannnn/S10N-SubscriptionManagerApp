# サブマネの全体構成と登録画面の説明

この説明は，添付の `README2.md` を前提に，サブスク登録画面をチームのアプリへ組み込むためのものです．会員登録・ログインも追加しています．認証の全体構成とAPI契約は [account_guide.md](account_guide.md) を参照してください．内訳・期限は雛形です．

## 1．全体で何が動くのか

**Androidアプリが画面を表示し，APIサーバがアカウントや登録情報を管理します．** Pythonで書いたFletの画面を端末に表示します．HTMLファイルをそのままAndroidアプリに組み込む構成ではありません．

| 層 | 役割 | 今回の対応 |
|---|---|---|
| 画面 | 検索，入力，選択，エラー，登録完了を表示する | `src/views/register.py` |
| 共通のアプリ土台 | 起動，画面の切り替え，共通ヘッダー・タブを管理する | `src/main.py`，`src/components/` |
| 共通の通信処理 | 画面からの要求をAPIへ送る．項目名の違いも吸収する | `src/api_client.py` |
| APIサーバ・DB | ログイン，ユーザごとの保存・同期，正式なサービスマスタを管理する | このプロジェクトの外で開発する |
| 公式サービス | 入会・退会の実際の手続きを行う | 後続の詳細画面から端末ブラウザで開く |

ホームも登録画面も，同じAPIクライアントを使います．登録画面が保存した後にホームが一覧を取得し直すため，新しいサービスが表示されます．本物のAPIへ接続すると，この要求の送信先がサーバになります．

## 2．ファイルを分ける理由

登録画面の中で通信，保存，画面切り替え，色の定義をすべて行うと，APIの仕様変更や別画面との統合で修正箇所が増えます．ガイドに合わせて，担当を分けています．

| ファイル | 何を書くか | 登録画面との関係 |
|---|---|---|
| `main.py` | アプリ起動と画面切り替え | 「追加」で登録画面を開き，完了後にホームへ戻る |
| `config.py` | ダミー使用の切り替え，API設定 | API未完成でも画面を作れる |
| `theme.py` | 色・フォント・余白の定数 | ホームと同じ見た目にする |
| `components/service_icon.py` | サービス画像，頭文字，時計・グレー表示 | 候補とホームのアイコンを同じ処理で表示する |
| `views/register.py` | 検索・入力・検証結果・登録イベント | 登録画面の本体 |
| `validation.py` | 必須項目，金額，日時，URLの検証 | UIとAPIクライアントから同じ検証を使う |
| `api_client.py` | 検索・登録・取得の通信と項目名の変換 | 各画面から直接HTTPを呼ばない |
| `dummy_data.py` | 検索候補と，セッション内の試用登録情報 | APIが完成するまで同じ操作を試す |

`register_view(page)` は **画面の中身のFletコントロールを返す関数** です．ヘッダーと下部タブは `main.py` が付けるため，登録画面の中で重複して作りません．

追加した `app_context.py` は，共通API，遷移関数，ログイン状態を1つにまとめる補助ファイルです．`main.py` が `page.data` に入れ，各画面が参照します．既存チーム実装が別の渡し方を使っている場合は，この接続部分を合わせれば登録フォームを流用できます．

## 3．登録するときの流れ

1. 未ログインで起動すると，アカウント画面へ入ります．「会員登録」でメールとパスワードを登録した後，同じ情報でログインします．ダミー版のアカウントはアプリ終了までだけ有効です．
2. ヘッダーの「追加」から，`main.py` が `register_view(page)` を表示します．
3. サービス名を入力すると，登録画面が `search_services(keyword)` を呼びます．候補を押すと，サービス名とマスタ内のアイコン・URL・メモを反映します．ダミーマスタは名前だけなので，料金・URLは手入力です．候補がないサービスも自由入力できます．
4. プラン名，月額・年額，税込料金，入会日・時刻を入力します．無料トライアル中なら，終了日時も入力します．
5. 登録ボタンで `validate_subscription(data)` が入力を確認します．不足や不正値があれば入力欄にエラーを表示し，通信しません．
6. 正常なら `context.api.create_subscription(data)` を呼びます．ダミー版では試用ストアへ，API版ではサーバへ登録します．
7. 成功した場合だけ「登録しました」を表示します．「ホームで確認する」でホームに移り，一覧を取得し直します．

検索は非同期で行います．入力が変わったら古い検索結果を捨て，画面移動後の結果が別画面へ反映されないようにしています．通信も `httpx.AsyncClient` を使い，待機中に画面全体を止めない構成です．

## 4．どのデータを渡すのか

項目名はガイドのsnake_caseに合わせています．以下の例の金額・サービス名は説明用の架空データです．

```python
data = {
    "name": "試用サービス",
    "plan_name": "個人プラン",
    "cycle": "monthly",
    "amount": 1000,
    "joined_at": "2026-10-05T11:00",
    "status": "trial",
    "trial_ends_at": "2026-11-05T11:00",
    "icon": "",
    "join_url": "",
    "cancel_url": "",
    "cancel_memo": "退会時にパスワードの準備が必要",
    "service_id": "選択した定番サービスのID",
}
```

`amount` は整数の円，`cycle` は `monthly` / `yearly`，新規登録時の `status` は `active` / `trial` です．登録一覧を受け取る側では `cancelled` も扱います．サブスク自身の `id` は保存側が決め，登録成功の返却データに含めます．

`trial_ends_at` と `service_id` は，ガイドの表にない追加案です．トライアル終了日時はガイド7章の扱いを実現するため，サービスIDは選択したマスタを区別するために使います．自由入力のサービスは `service_id` を送らず，通常契約の `trial_ends_at` は `None` にします．API担当と正式なフィールド名を確認してください．

パスワード自体は登録項目にありません．退会メモには準備が必要という案内だけを書きます．

## 5．ダミーからAPIへ変えると何が変わるか

画面の呼び出しは同じです．`api_client.py` の内部だけが，ダミーストアへの操作からHTTPS通信に変わります．したがって登録画面が「ダミーならこの処理，本物なら別の処理」と分岐する必要はありません．

切り替える前に確認する内容は，ガイド5章と同じです．APIのURL，認証方法，各ルート，項目名，日時の書式，返却形式を決めます．今回の通信ルートは正式仕様ではなく，接続例です．

| 画面から使う関数 | 今回の仮ルート | 返してほしいもの |
|---|---|---|
| `search_services(keyword)` | `GET /services?keyword=...` | サービス辞書の配列 |
| `create_subscription(data)` | `POST /subscriptions` | 保存した1件の辞書．`id` を含む |
| `list_subscriptions()` | `GET /subscriptions` | 登録サブスク辞書の配列 |
| `get_subscription(sub_id)` | `GET /subscriptions/{id}` | 登録サブスク1件の辞書 |

正式APIが `{"items": [...]}` のように包んだ形で返す場合も，画面ではなく共通クライアントで配列を取り出します．APIの項目名が違う場合は `normalize_subscription()` の変換表を合わせます．

通信が失敗したときは，ダミー保存に切り替えず，入力を残してエラーを表示します．サーバに保存できたという誤解を避けるためです．アプリには会員フォームと認証クライアントを実装済みです．サーバ側での認証・入力検証・ユーザごとのアクセス制御は別開発のAPIと接続します．

## 6．今回保留にしていること

ガイド7章では，更新日や支払い見込みをアプリ側とAPI側のどちらで計算するか未定です．そのため今回の日付処理は「入力が正しいかの確認」に限り，次回更新日や金額見込みは計算しません．`src/logic/` と日付・支払い計算のテストは，担当が決まってから追加します．

今回のホーム・読み取り専用詳細は登録結果の確認用です．編集・削除，公式サイトを端末ブラウザで開く処理，内訳，期限の完成実装は各担当者と統合してください．会員画面の担当との統合方法は [account_guide.md](account_guide.md) に記載しています．チームの既存ファイルを上書きする前に，共通の渡し方とFletの固定バージョンを共有してください．

## 7．確認できたことと，これから確認すること

固定したFlet 1.0.3で，Python側の画面構築・イベントと通信処理の59件のテストが通っています．会員登録・ログイン・ログアウト，ユーザ別データ，起動画面，検索候補，登録完了，ホームへのデータ反映，日付・時刻ピッカー，通信エラーと二重送信防止を確認しました．Flet 1.0.3の入力欄は `error` プロパティでエラーを表示します．同梱フォントの配信も確認済みです．

Android実機での画面幅，文字サイズ，キーボード表示，カレンダーと時刻選択，横スワイプ，戻る操作は手動確認が必要です．APKのビルド，正式APIとの通信，同じアカウントの2端末同期も未確認です．PCでの開発は `flet run`，実機での開発用表示は `flet run --android`，APK作成は `flet build apk --python-version 3.12` の順で進められます．
